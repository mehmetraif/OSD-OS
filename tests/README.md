# Regression tests

Thirty-two test suites, built apart from the app; one of them starts the app itself, on the main menu and on each module. CI runs them on Linux x64 and arm64 for every pull request that touches `src/`, `scripts/`, `Main.qml`, `views/`, `modules/`, `assets/`, `shaders/`, `tests/`, `thirdparty/` or the build ([regression-tests.yml](../.github/workflows/regression-tests.yml)): on Ubuntu, with the oldest Qt the releases are built with (6.4), and on Raspberry Pi OS (Debian 13 "trixie" with Raspberry Pi's archive, arm64), the system the OS image is made of, with the Pi's own Qt (6.8) and mpv (0.40). The release workflow runs them too, on the tagged commit, and publishes no release that fails them, though its builds are made ([release.yml](../.github/workflows/release.yml)); and the FreeBSD and OpenBSD build workflows run them in their virtual machines, with the systems' Qt 6.11 ([freebsd.yml](../.github/workflows/freebsd.yml), [openbsd.yml](../.github/workflows/openbsd.yml)). They need Lua 5.4, CMake, a C++17 compiler, Qt 6's development packages (Core, Concurrent, Gui, Network, Qml, Quick, QuickTest and Test) and SDL2's, libdrm's on Linux, zlib's and minizip's for **highscores** (`libminizip-dev`; without them that suite is left out, with a warning), and Qt's D-Bus module (in `qt6-base-dev`) and `dbus-daemon` for **wifi** (without the module that suite is left out, with a warning; without `dbus-daemon` it skips itself); the QML tests also need Qt Quick's QML modules at run time (on Debian and Raspberry Pi OS, `qml6-module-qttest qml6-module-qtquick qml6-module-qtqml-workerscript qml6-module-qtquick-window`). None needs mpv, FluidSynth, MAME, NetworkManager or a display. The **app** tests start the app, built first in `build/` as [BUILDING.md](../BUILDING.md) has it (`-DOSDOS_APP=<path>` for one elsewhere), with the QML modules it runs with (a module that imports one this Qt doesn't have is skipped; but Qt Quick 3D, which only the Arcade screen's Orb look imports, and which the app goes on without).

```sh
cmake -S tests -B build-tests
cmake --build build-tests --parallel
ctest --test-dir build-tests --output-on-failure
```

- **app** (`app_smoke_test.sh`; `app_main_menu`, `app_setup_file`, and `app_module_<folder>` for each module in `modules/`): the app itself, started offscreen on a data folder of its own, every proxy a dead port.
  - The main menu with every module on it, and each module as the startup module, comes up (Qt's import trace names its view), and up to the shutdown the app prints no QML warning: no error in a binding or a script, no type, QML module or file missing, no value that can't be assigned.
  - With an OSD/OS Setup file in the data folder (`app_setup_file`), the app takes it as it starts: OSD/OS Setup's notice comes up (`views/SetupNotice.qml`), the file is gone, its setting is in `config.json`, and the log says what was set.
  - SIGTERM stops it within 15 seconds, with 143 (128 + the signal), as the service's stop helper expects.
  - Skipped without the app, and for a module that imports a QML module of Qt's the Qt in use doesn't have.
- **app_core_info** (`app_core_info_test.sh`, where the arcade test's core is built): the app asked a libretro core's name and version (`--core-info`), as the Arcade module asks a copy of it, with nothing of an environment (no display, no platform for Qt, no data folder): it prints the test core's (`arcade_test_core`), and refuses a file that isn't a core, saying why. ## A stand-in NetworkManager for screenshots

`fake_networkmanager`, built with the tests and never run by ctest, is **wifi**'s stand-in on its own. It registers as NetworkManager on the bus whose address it is given, else the one `DBUS_SYSTEM_BUS_ADDRESS` names, and runs until it is killed, with five networks heard: Home, saved and joined; Workshop, saved; Arcade Hall (WPA3, password `insert-coin`), Corner Cafe (open) and Neighbours (WPA, password `not-yours-42`), each with its own number of bars. Each step of joining takes a second and a half, so that a network on its way can be seen. The app shows them in Settings → Wi-Fi with that bus as its system bus (on Linux, the app built with Qt D-Bus, without `OSDOS_AUTOSTART`):

```sh
export DBUS_SYSTEM_BUS_ADDRESS=$(dbus-daemon --session --fork --print-address=1)
build-tests/fake_networkmanager &
APP_ROOT=$(pwd) ./build/osdos
```

For the country's line, point `OSDOS_BOOT_DIR` at a folder whose `cmdline.txt` has `cfg80211.ieee80211_regdom=GB`. Kill the stand-in and that `dbus-daemon` once done.

## On a Raspberry Pi

What the tests can't reach, above all the screen changing hands (DRM and the VT), wants checking on the device:

- Search a large USB or NAS library while moving about the menus. The menus keep up, and no more than 200 results are kept.
- Start A, then B, then C quickly (NFC cards, say). Only C plays, once A has gone, and the menus never freeze meanwhile.
- Press back while the next video waits for the old one. Nothing starts, and the menus come back about 200 ms after the old player has gone. Repeat with Transparent Background on.
- Tap a card just as a video ends. The new one plays, and the menus don't take the screen from it.
- Hide the active VT from the app (neither `/sys/class/tty/tty0/active` nor `/dev/tty0` open to it) and play two videos in a row. The log says the VT is not switched, both play, and the menus come back on the VT they were on, not one further on each time.
- Cut the power while settings are being changed and while a video's resume point is saved. Every file comes back as the old JSON or the new, never cut short.
- Cut the power during a new card's first boot once its film partition is made, before it is formatted. The next boot formats it (`The film partition has no filesystem: formatting it` in the boot log) and it mounts as OSD-OS, empty; a film partition blkid finds any filesystem on is left as it is.
- Fill the data folder, or make it read-only. A save then logs why and leaves the old file.
- Choose an output with At Next Start, then switch the Pi off at the wall: it starts on the new output and asks to keep it. Choose one with Switch and Power Off: it powers off, and starts on it.
- With a Raspberry Pi to JAMMA board and JAMMA 240p, on a Pi 4 and on a Pi 5 (its sound through a USB sound card): the picture holds on the cabinet's monitor in the right colours, the sound comes from its speaker, `osdos-jamma --test` names each control as it is pressed, and both players' joysticks and buttons move the menus and reach a game.
- Plug in two keyboards (or a keyboard and a remote's dongle) and pair a Bluetooth one: each is listed in Settings → Controls under its own name as it comes, ◄ follows the one typed on, a key set on one's page works on it and not on the other, and a remote's Home or Menu button can be set on its page.
- With several pads, the JAMMA board's two sticks among them: each pad's page shows its buttons by its labels (Auto), a button set on one pad does that action on it alone, and the hints follow the pad used last.
- Pick each theme with music, on the sound card in use: the music starts a moment after, stops the moment a video starts (and while it loads, and under its menu), and starts again back in the menus. A MIDI theme's first start waits for FluidSynth a few seconds.
- Move about the menus with each theme: the effects keep up at the CRT's 480 lines, and none of them, nor the music, shows or plays while a video does.
- With Transparent Background, play ten films in a row, each from the last one's Browse. The log's `[MpvController] memory as a video starts` lines stay about level, and no `[watchdog]` line comes.
- Hold Esc on the main menu for a second. Settings opens once and stays open.

- **osc_controls** runs the actual menu script at five output sizes with and without subtitles; verifies menu and seek bindings, including Lua 5.4 fractional-coordinate formatting.
- **reliability** exercises Audio Output's note without a USB sound card (nothing plugged in, a device ALSA made no card of, the Pi's power too low by its firmware's flags or the hwmon's alarm), a card put at its full level through a stand-in amixer on a thread of its own (the controls raised, one already full only looked at, none run without the stand-in), `config.json` read once while its time and size stay and afresh after a save or an edit by hand, Audio Output on Auto where ALSA's default card can't play (a Pi 5's HDMI without the picture: the USB card, or the HDMI port with the picture, given a process as `ALSA_CARD` and a video inside the app as its device; nothing while card 0 plays, or while an ALSA configuration or `ALSA_CARD` sets the default; a card chosen as chosen, one unplugged as on Auto), stale geocoding callbacks, failed update marker writes, update versions compared by number (a prerelease below its release, an older release never offered), fsync errors, asynchronous directory cache invalidation, atomic download replacement under a file-size limit, download-owner destruction, the release file each system's updater takes (Windows' zip named, not taken), the log file the Windows build keeps (what was logged before the data folder was known, and the run before's beside it), and OSD/OS Setup's file on a computer: checked as the card checks it (too big, not JSON, a number JSON can't hold, an unknown version, a BOM, the account's rules, what a card alone sets named), taken as the app starts from the data folder and deleted before anything of it is set, `config.json` merged and the account written owner-only, and pasted in Settings (`AppCore::applySetupText()`): each changed setting announced, a submenu's by its dotted key, the account handed on, and text that isn't the page's changing nothing.
